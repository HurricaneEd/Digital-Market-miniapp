# DigRecSys 面试技术问题整理

以下答案只基于当前项目实际实现，不包含不存在的 Vue 管理端、微信登录或真实支付。

## Web 与 API

### 页面、API、数据库之间如何流转？

微信小程序通过集中封装的 `wx.request` 调用 Django REST API。Router 把 URL 分发到 ViewSet，Serializer 负责输入校验和响应字段，ORM 操作 MySQL。需要认证的请求使用 DRF Token 请求头。商品采集不走这条交易链路，而是先输出原始批次，再由入库工具校验后写入商品目录。

### 为什么这样设计分页？

公共 API 使用 DRF 全局页码分页，每页 12 条，适合小程序按页加载。管理员商品和用户接口使用独立分页器，每页 10 条并允许受限的 `page_size`，方便管理操作。分页在服务端完成，可以保持响应大小稳定；前端根据 `next` 决定是否继续加载。

### 表单数据如何校验？

第一层是 Serializer，例如手机号格式、购物数量、订单创建参数和 `all_params` JSON 结构。第二层是 Model 字段与 `full_clean()`，例如分类循环。第三层是数据库唯一约束、检查约束和外键。订单创建还使用事务和行锁处理库存，避免只依赖页面校验。

### 前后端字段不一致如何排查？

先检查实际网络响应，再依次核对 Serializer 的显式字段、ViewSet 使用的 Serializer、小程序 `utils/api.js` 和页面绑定。阶段 3 的 `origin` 就按 Model → Migration → Serializer → API 响应 → WXML 的顺序验证，并增加接口测试避免只看页面猜测。

### 为什么公共商品和管理商品使用两个 ViewSet？

公共商品只读，并且只返回在售商品；管理员商品接口需要 CRUD、搜索、排序和批量上下架。分开后权限和可见性规则更清楚，也避免在一个 ViewSet 中堆积大量按角色分支。

### Token 认证的优缺点是什么？

当前实现简单，适合项目的账号密码登录和小程序请求封装。缺点是 Token 长期有效、没有刷新机制，也不等于微信身份认证。正式微信场景需要设计 `wx.login`、code2Session、openid 绑定和 Token 生命周期。

## 数据库与交易

### User、Product、Order 之间是什么关系？

用户拥有地址、购物车项、订单和评论。购物车项关联一个用户和一个商品，并对用户与商品建立唯一约束。订单属于用户，订单下有多个订单明细；订单明细可以关联当前商品，但同时保存下单时商品编码、名称、价格和数量快照。

### 为什么商品使用固定字段加 all_params JSON？

价格、库存、品牌、分类、上下架和产地属于稳定业务事实，需要明确字段和约束。不同数码品类的参数结构差异较大，当前只用于详情展示，因此保留在 `all_params`，避免过早建立复杂 EAV。只有出现稳定的跨商品筛选需求时，才把具体参数投影为可查询字段。

### 为什么新增商品字段需要 Migration？

修改 Model 只改变 Python 定义，数据库表不会自动变化。Migration 把结构变化版本化，使开发、测试和新环境按相同顺序得到一致表结构。阶段 3 新增 `origin` 使用独立 `0004`，没有重写已应用迁移。

### 老数据如何兼容？

`origin` 定义为可为空并默认空字符串，因此 48 条旧商品迁移后仍可读取。小程序把空值显示为“未填写”。没有从名称或动态参数猜测产地，也没有让旧导入文件清空后来人工维护的值。

### 订单为什么需要快照？

商品价格、名称和收货地址在下单后可能变化。订单明细和收货地址快照保存交易发生时事实，历史订单不能根据当前商品或当前地址反向覆盖。

### 库存一致性怎么保证？

订单创建在事务中校验购物车和库存，扣减成功后创建订单和快照并删除对应购物车项；任一步失败都会回滚。取消订单只允许特定状态并恢复一次库存，测试覆盖库存不足和重复取消。

## AI Coding

### Codex 在项目哪些阶段使用？

用于代码审计、需求影响分析、Task List、实现候选修改、测试编写、Bug 根因定位和文档整理。数据库迁移、接口行为和测试结果都通过真实命令确认，不把模型描述当作运行事实。

### AI 写错代码怎么办？

保留小步差异，先运行定向测试，再运行关联回归。阶段 3 编写测试时曾发现一段测试代码插入位置不正确，在生产代码回归前通过文件检查纠正；最终结果以实际测试输出为准，而不是默认生成代码正确。

### 怎么判断 AI 生成结果正确？

检查五类证据：是否符合现有模型和业务术语、Migration 是否与 Model 一致、API 契约是否与客户端一致、数据库不变量是否有测试、GUI 未执行部分是否明确标记人工验证。还要检查最终差异没有覆盖用户原有修改。

### 如何把 Bug 描述给 AI？

至少提供环境、前置数据、可复现步骤、期望结果、实际结果和错误输出。对于数据问题还应说明是否允许写库，以及测试数据是否必须回滚。这样的信息可以把“页面不对”转成可验证的接口或状态断言。

### 为什么先生成 Task List，而不是直接写代码？

因为一个字段可能影响数据库、Serializer、写接口、读接口、客户端和旧数据。Task List 先暴露遗漏和兼容风险，也明确哪些模块实际不存在，避免为了满足模板凭空增加后台页面。

## 真实 Bug：公共 API 暴露下架商品

### Situation

小程序客户端会过滤下架商品，但公共 API 的查询集没有在售条件，服务端分页仍包含下架数据。

### Task

保证用户侧列表和详情隐藏下架商品，同时不能影响管理员维护下架商品。

### Action

在回滚事务中创建 `is_active=False` 商品，确认列表 `exposed=True`、详情 HTTP 200；然后为公共查询增加 `is_active=True`，保留管理员查询集，并新增覆盖列表、公共详情和管理员详情的回归测试。

### Result

复测公共列表 `exposed=False`、公共详情 HTTP 404、管理员详情 HTTP 200；Product 7 项和全量 15 项测试通过。完整证据见 [05_BUG_LOG.md](./05_BUG_LOG.md) 和 [06_REGRESSION_REPORT.md](./06_REGRESSION_REPORT.md)。
