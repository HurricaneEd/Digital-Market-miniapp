# 阶段 3：商品产地字段需求

## 1. 需求目标

为线上商品增加“产地”信息，使管理员可以通过现有商品管理 API 在新增或编辑商品时维护产地，公共商品接口和微信小程序商品详情可以读取并展示该字段。

统一字段名为 `origin`，面向用户显示名称为“产地”。

## 2. 当前实现核查

- `Product` 当前没有 `origin`、产地、原产地或其他同义固定字段。
- `all_params` 可能保存来源规格，但它不是产地的稳定业务字段，不应成为新的第二事实来源。
- 当前存在公共商品列表/详情 API 和管理员商品 CRUD API。
- 当前不存在可操作的商品后台页面，也没有 `Product/admin.py`；本需求不凭空新增后台前端。
- 微信小程序已有商品详情页，可以增加产地展示。
- 商品入库器当前没有可靠的产地来源列。

## 3. 字段定义

| 属性 | 定义 |
| --- | --- |
| ORM/API 名称 | `origin` |
| 数据库类型 | `VARCHAR(100)` |
| 是否必填 | 否 |
| 旧数据默认值 | 空字符串 |
| API 空值 | `""` |
| 小程序空值展示 | `未填写` |

产地是文本描述，不在本阶段拆分国家、省、市等结构，也不增加产地筛选和索引。

## 4. 影响范围

### 数据库与 ORM

- 在 `catalog_products` 增加非空 `origin` 字段。
- 使用空字符串作为默认值，保证已有商品可以无损迁移。
- 新增迁移，不修改或重写已应用迁移。

### Serializer 与 Schema

- `ProductSerializer` 明确加入 `origin`。
- `AdminProductSerializer` 继承该字段，因此管理员商品新增和编辑接口可写入产地。
- DRF/OpenAPI Schema 随 Serializer 自动反映字段变化。

### 商品接口

- 公共商品列表和详情返回 `origin`。
- 管理商品新增、全量编辑和局部编辑接受 `origin`。
- 超过 100 个字符应返回校验错误，不写入数据库。

### 后台页面

当前项目没有商品后台页面，因此后台列表、表单和详情页面标记为 `NOT_IMPLEMENTED`，本需求不新增不存在的前端模块。

### 微信小程序

- 商品详情“商品信息”区域增加“产地”。
- 空字符串显示为“未填写”，避免旧商品出现空白行。

### 商品导入

本阶段不修改 `database/import_products.py`。现有原始/清洗数据没有稳定的 `origin` 输入契约；保持导入器不写该字段，可以避免旧批次重新导入时清空管理员已维护的产地。后续确认来源列后再增加条件更新规则。

## 5. 向后兼容

- 原有 API 字段不删除、不改名。
- 新增字段为可选字段，旧客户端可以忽略。
- 已有商品迁移后 `origin=""`，不会因缺少产地而失败。
- 原有商品导入、购物车、订单和评论逻辑不依赖产地。

## 6. 验收标准

1. 迁移可以在现有数据库上执行，旧商品全部保留。
2. 新建商品可以保存并返回 `origin`。
3. 编辑商品可以修改并回显 `origin`。
4. 超长产地值返回 HTTP 400，原值保持不变。
5. 公共商品详情返回 `origin`。
6. 小程序商品详情显示产地；空值显示“未填写”。
7. Product、Orders、Users 和全量回归测试通过。

## 7. 非本次范围

- 新建后台管理前端。
- 对旧商品批量推断或编造产地。
- 按产地搜索、筛选、统计。
- 从 `all_params` 自动抽取产地。
- 修改采集器或强制旧导入文件提供产地。
